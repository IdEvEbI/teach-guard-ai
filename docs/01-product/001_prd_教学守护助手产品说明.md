## 1. 问题陈述

听课、带教复盘和示范课抽检高度依赖个人经验，难复制。样片一多，就难以对每一段视频给出稳定、可执行的反馈。教学守护助手把「听懂讲了什么 → 对照课型与教学标准 → 给出改法」做成可重复的本地流水线：一条路径精查单个视频，一条路径扫描整天目录。

本仓是前身课评工程仓的**替代产品**，全新实现，不复制前身仓代码。标准与方法仍以上游文档仓为准，不在本仓另立一套「好课」总标准。

## 2. 用户、形态与处事风格

| 项       | 说明                                                                                    |
| -------- | --------------------------------------------------------------------------------------- |
| 第一用户 | 维护者本人：自测口径、抽检示范课、迭代提示词                                            |
| 后续用户 | 分校带教（精查报告可用之后再内测）；全体教师自查不在当前范围                            |
| 形态     | **本地 CLI**；无账号、无门户、不接入公开绩效考核                                        |
| 场景     | 线下现场培训与线上培训（具体品牌不在本仓展开）                                          |
| 媒介     | 默认**共屏（桌面共享）**：PPT、笔记软件、集成开发环境推送到学员屏幕；**不使用黑板板书** |
| 课型     | 见第 5 节枚举（六课型 + 阶段第一课开场 `stage_first`）                                  |

报告与产品文案必须遵守：

1. 以建立可复用系统为导向，输出可执行改法，避免只堆批评。
2. 三不三要：不公开批评校区负责人或教师；不越级指挥一线；不只带问题走；要私下对齐；通过校区负责人推动；带方法走。
3. 对事不对人；报告默认私密。
4. 合格线（必须改）与水平线（锦上添花）分开写；禁止把发展项写成进班否决语气。
5. 先保证可读，再追求简短；使用完整句子；禁止电报体。
6. 公开仓脱敏：不写维护者真名、所在机构或对外品牌名。

## 4. 单视频：`inspect`

命令约定（实现时写入 CLI 契约，本文先锁产品名）：

```bash
uv run teach-guard inspect <视频或音频文件>
```

### 4.1 输入

- 一个视频文件，或已经分离好的音频文件。默认放在 `data/input/`（已 gitignore）；相对路径会先看当前目录，再看该目录。
- 不自动寻找「同一模块」的其他文件；模块关系由目录批量或维护者另行指定。

### 4.2 核心流水线（必须能跑通）

1. **抽音轨**：若输入是视频，分离为 mp3（或等价音频）；若输入已是音频，可跳过。
2. **转写**：基于音频生成带时间信息的逐字稿。默认本机 **mlx-whisper**（`large-v3-turbo`）；不使用云端语音识别。
3. **标点（不改词）**：将逐字稿交给 DeepSeek（OpenAI 兼容 API）补标点，得到可供人读、并供后续步骤使用的标点稿。本步**只补标点**，不得替换数字、型号、专名，也不得把边敲边讲的工具口述（例如「写下」「向右」）改写成连贯讲稿。全文纠错不做。原始 `.raw.md` / `.raw.json` 是证据层，不得覆盖。
4. **识别视频类型**：对照第 5 节枚举给出主类型；维护者可用 `--type` 覆盖。判不准时记为 `other`，并在产物中说明依据不足。阶段第一课开场（含只录了「学什么」的片段）用 `stage_first`，**不要**判成简介类。
5. **概念与示例**：检查讲解中的概念是否准确、示例是否有效且贴合当段交付点。无逐字稿摘句，不得写成合格线「必须改」。
6. **提炼讲解结构**：写出本段结构（宜有总分总与清晰主交付）。仅有总分总外壳、主线不清时，须给出可执行改法，而不是只写「结构不好」。
7. **提升建议**：对照上游薄标准与对应课型专文，给出可执行的优化建议。合格线与水平线分栏。**分数评定后置**，本阶段报告不打课研百分制，也不输出进班否决语气的等第。

### 4.3 核心输出

默认写在本地 `data/output/`（已 gitignore）。每次 `inspect` 按输入在 `data/input/` 下的相对路径建立运行目录（去掉扩展名作为末级目录名，例如 `data/input/01_课/day01/大纲.avi` → `data/output/01_课/day01/大纲/`），至少包括：

| 产物       | 说明                                                                                                     |
| ---------- | -------------------------------------------------------------------------------------------------------- |
| 原始逐字稿 | `{stem}.raw.md` / `{stem}.raw.json`，带时间锚；本步不补标点、不改原词                                    |
| 标点逐字稿 | `{stem}.punct.md` / `{stem}.punct.json`，带时间锚；只补标点，不改词                                      |
| 结构说明   | 本段课型与主交付假设（`{stem}.type.md` / `{stem}.type.json`）                                            |
| 建议报告   | `{stem}.report.md` / `{stem}.report.json`：现场结构、概念与示例、合格线 / 水平线、待回放确认；**不打分** |
| 运行清单   | 输入哈希、ASR / LLM 型号、提示词版本                                                                     |

专业判断默认只基于转写与标题锚点。共屏画面、做课材料是否齐备、未截到的后半段，写入「待回放确认」，不得仅凭稿子写成合格线必改。改法中禁止默认「板书一下」，应写共屏 PPT、笔记或集成开发环境中的具体动作。

### 4.4 凭逐字稿能判与不能判

本阶段录音默认只录屏幕，往往没有学员声道。边在结构图或笔记里打字边讲，是共屏授课的常态；短句、停顿不等于表达不流畅。

| 能凭稿子写进报告的                                                                                                         | 不得仅凭稿子写成合格线必改的                                                                                                                                      |
| -------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 口头逻辑（引入、展开、收束）；术语是否先通俗后专名；老师发出的提问、设问、留白形态；空问（如「听懂了吗」）；讽刺挖苦等话术 | 吐字、音量、语调、坐姿；目光覆盖与学员是否跟上；学员有没有接住互动                                                                                                |
| **现场兑现的课程设计**：主交付、模块切分、口头 Why / What / How、与课型硬项的差距                                          | **备课产物是否齐备**（当天结构图、讲义、PPT、视频列表、设计图、试录是否交齐、带教是否确认）。对齐上游一天备课与自检清单是材料验收，不是本工具单视频精查的通过标准 |

沟通力在本阶段只评**老师发出的交互形态**，不评「课堂上是否发生了双向沟通」。后者写入待回放确认。

课程设计只提炼现场结构，不拿备课产物清单当合格线；老师自备结构图与讲义的对照放到升级能力。

### 4.5 升级能力（核心稳定后再做）

| 项         | 说明                                                                                                                                    |
| ---------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| 结构优化稿 | 参考上游标准给出结构调整建议，生成**可导入 XMind 的 Markdown 标题树**                                                                   |
| 讲义       | 针对逐字稿与讲解知识内容，生成 Markdown 讲义，供学员复习或教师改课                                                                      |
| 类 PPT     | 使用前端技术，把 Markdown 讲义变成可全屏播放的幻灯片。具体框架（Slidev / reveal.js / Marp 等）在进入该里程碑时用 ADR 锁定，不在 M0 选型 |

升级产物仍落在 `data/output/`，不入库。

## 5. 课型枚举

现场组织知识点视频时，每一个视频标注**一个主类型**。本仓 CLI 与报告使用下列枚举，与上游备课方法 `001`、`004` 及 `005`～`010` 专文对齐。

| 枚举          | 上游类型       | 学员学完后应达到的能力（摘要）             | 时长与结构的常用合格线（摘要，细则以上游专文为准）     |
| ------------- | -------------- | ------------------------------------------ | ------------------------------------------------------ |
| `stage_first` | 阶段第一课开场 | 理解本阶段学什么、老师能带来什么、班级约定 | 开场四部分合计约 30～40 分钟；「学什么」约 15～20 分钟 |
| `intro`       | 简介类         | 建立背景与用语，能衔接后续学习             | 约 10～15 分钟；勿讲成百科或完整原理课                 |
| `practice`    | 实操类         | 能按路径操作并得到可用结果                 | 演示与随堂合计不超过一节课；禁止只念 PPT               |
| `syntax`      | 代码语法类     | 能按单点语法从 0 到 1 写出可运行代码       | 一知识点一视频约 10～20 分钟                           |
| `case`        | 案例类         | 能综合应用当天核心知识点完成可运行小业务   | 按需求、选型、分步实现并验证推进                       |
| `principle`   | 原理类         | 能判断、能解释，而不是只背定义             | 一交付点一视频；单段不超过 30 分钟                     |
| `project`     | 项目类         | 在接近企业实践的完整交付中综合运用已学知识 | 开篇与模块实现按专文切分；勿把项目课讲成语法课         |
| `other`       | 无法判定       | 维护者校准                                 | 报告须写明依据不足，不得假装高置信                     |

`stage_first` 不是简介类。阶段地图、开场四部分（学什么 / 自我介绍 / 班级约定 / 今日目标）回链上游 004；某一知识模块前的短铺垫才回链 005。文件名含「大纲」「介绍」「了解」时，仍须先看口头主线是不是阶段地图。

固定环节（每日反馈、作业讲解、全天总结等）不是当天主体教学内容；批量扫描可标注，不要用六课型硬套，记为 `other` 并说明。

## 6. 目录批量：`scan`

```bash
uv run teach-guard scan <目录>
```

### 6.1 输入约定

- 目录视为**同一授课日**的视频集合。工具**不**自动判断「这些文件是否真的属于同一天」；由使用者保证选对目录。
- 处理顺序：按文件名**前缀数字**升序。缺号或重号时发出警告，仍按可解析数字排序；无法解析的文件放到末尾并在报告中列出。
- 依次扫描，不并行打满本地模型，以便维护者观察进度与中断。

### 6.2 核心能力（必须能跑通）

1. **记录每个视频的时长**。
2. **判断每个视频的类型**（第 5 节枚举；可校准）。
3. **言行底线扫描**：检查是否出现低俗用语、贬低学科课程、贬低上一任老师等违规表述。判定对齐上游 A07；须有逐字稿摘句。无摘句不得写成「必须改」。
4. **时长与结构**：对照该课型常用时长与「是否有可感知的开头、主交付、收束」做完整性检查。结构检查在批量路径上从简，避免把整天扫描做成 N 份完整精查。
5. **生成全天扫描报告**：一张总表（文件名、时长、课型、言行是否触线、时长是否合理、结构是否明显残缺）+ 摘句附录。

批量路径**默认不**跑单视频核心的概念预审与完整教练建议，以免一整天视频耗时不可控。维护者对总表中的异常条目，再单独执行 `inspect`。

### 6.3 批量输出

`data/output/<目录名>/summary.md`，以及各段必要的转写 / 扫描 JSON。真实课例不进 Git。

## 7. 明确不做

- 全员自查门户、账号体系、复杂权限
- 与公开绩效考核挂钩
- 自动判断视频是否属于同一天或同一模块
- 云端语音识别作为默认路径
- 把课研评分表当作本阶段是否通过的判定标准，或在报告里打百分制分数（后置）
- 生成正式授课成片、把类 PPT 升格为当期必交付
- 在 Git 中存放真实课例媒体或密钥
- 把本仓写成第二份组织级标准文档仓
- 复制前身仓代码作为实现起点

## 9. 成功标准

### 9.1 单视频核心何时算过关

维护者选定的真实课例（至少覆盖两种课型，其中宜含一段阶段第一课开场）上，能稳定产出标点稿、课型、结构与可执行建议。建议读起来像带教在说话，能指出主交付或课型硬项上的具体缺口，而不是「表达更清晰」一类套话。维护者愿意用它改课或抽检，而不是演示一次后搁置。

### 9.2 目录批量何时算过关

对一个授课日目录，能在可接受时间内给出总表：每条视频的时长、课型、言行触线摘句、明显的时长或结构异常。维护者能凭总表点选 1～2 段再跑 `inspect`。

### 9.3 单视频升级何时算过关

同一段已通过核心流水线的课例，能额外得到维护者愿意拿去改课的结构 Markdown（可导入 XMind）与讲义 Markdown。类 PPT 另立验收，不阻塞前两项。
